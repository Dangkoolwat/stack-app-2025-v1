# Git Workflow

## 목적
이 문서는 에이전트가 수행한 작업을 안전하게 검토하고, 필요 시 쉽게 롤백할 수 있도록 Git 기반 작업 흐름을 정의한다.

---

## 기본 원칙

- 에이전트는 직접 main/master 브랜치에서 작업하지 않는다.
- 모든 작업은 별도 작업 브랜치에서 진행한다.
- 작업 완료 후에는 코드 변경, agent-log, 필요한 문서 변경을 함께 남긴다.
- 리뷰는 전체 코드를 처음부터 끝까지 보는 방식이 아니라, 요약 → 위험도 → 상세 확인 순서로 진행한다.

---

## 브랜치 전략

### 작업 브랜치 생성 규칙
아래 형식을 권장한다.

```bash
agent/<area>-<task-name>
```

예시:
```bash
agent/backend-user-cache-refactor
agent/frontend-order-list-fix
agent/security-auth-header-hardening
```

### 브랜치 사용 규칙
- 하나의 작업 브랜치에는 하나의 작업만 담는다.
- 설정 변경, DB 변경, 보안 변경, 라이브러리 업그레이드는 가능하면 별도 브랜치로 분리한다.
- 큰 작업은 여러 브랜치로 나누어 순차적으로 검토 가능하게 한다.

---

## 작업 완료 시 필수 산출물

에이전트는 작업 완료 시 아래를 함께 남겨야 한다.

- 코드 변경
- agent-log
- 코드 내 변경 이력 주석 (필요 시)
- OpenAPI 변경 (API 계약이 바뀐 경우)
- 테스트 결과 요약

---

## agent-log 위치 및 필수 파일

작업 성격에 따라 아래 위치에 생성한다.

```text
docs/{backend|frontend}/agent-log/YYYY-MM-DD-task-name/
```

필수 파일:
- problem-analysis.md
- proposal.md
- self-check.md
- implementation-plan.md
- walkthrough.md
- final-report.md

작성 원칙:
- 모든 내용은 한국어로 간략히 작성한다.
- 기술 용어, 클래스명, 라이브러리명 등은 영어 유지 가능하다.
- 긴 설명보다 변경 이유와 영향 중심으로 기록한다.

---

## 커밋 규칙

### 커밋 전 체크
아래 조건을 만족한 뒤 커밋한다.

- agent-log 작성 완료
- 테스트 결과 정리 완료
- 필요한 코드 주석 반영 완료
- OpenAPI 변경 여부 확인 완료
- 롤백 가능 여부 확인 완료

### 커밋 메시지 권장 형식

```bash
type: 작업 요약
```

예시:
```bash
feat: 사용자 조회 성능 개선 및 agent-log 추가
fix: 인증 캐시 제거 및 TTL 정책 재설계
refactor: 주문 조회 로직 정리 및 문서 업데이트
docs: git workflow 및 리뷰 규칙 추가
```

권장 type:
- feat
- fix
- refactor
- docs
- chore
- test

## 리뷰 흐름

리뷰어는 아래 순서로 검토한다.

### 1. final-report.md 먼저 확인
가장 먼저 아래 항목을 확인한다.

- 무엇을 바꿨는가
- 왜 바꿨는가
- 영향 범위는 어디인가
- 테스트 결과는 어떠한가
- 후속 작업이 있는가

### 2. 변경 파일 목록 확인
다음 중 고위험 영역이 포함되었는지 확인한다.

- Config / Env
- Security / Auth
- Cache / Redis
- Database
- OpenAPI
- Dependencies

### 3. 필요 시 상세 문서 확인
이상이 있거나 고위험 변경일 경우 아래 문서를 추가 확인한다.

- self-check.md
- problem-analysis.md
- walkthrough.md

### 4. 마지막에 코드 상세 확인
모든 작업을 코드부터 상세히 읽지 않는다.
요약과 영향 범위를 먼저 보고, 필요할 때만 코드 상세로 내려간다.

---

## 변경 등급 기준

모든 작업은 아래 3단계 중 하나로 분류한다.

### Level 1 — 경미한 변경
예:
- 문구 수정
- 스타일 수정
- 단순 UI 조정
- 명백한 오타/버그 수정

처리 기준:
- 간략한 agent-log 작성
- 빠른 리뷰 가능

### Level 2 — 일반 기능 변경
예:
- 서비스 로직 수정
- API 내부 처리 개선
- 화면 기능 추가
- 쿼리 개선

처리 기준:
- 전체 agent-log 작성
- 테스트 결과 필수
- final-report 중심 리뷰

### Level 3 — 고위험 변경
예:
- 설정 변경
- 라이브러리 업그레이드
- 인증/보안 변경
- 캐시 정책 변경
- DB 스키마 변경
- API 계약 변경

처리 기준:
- Global Impact Review 필수
- 롤백 계획 필수
- 코드 주석 필수
- OpenAPI/문서 동기화 필수
- 상세 리뷰 필요

---

## 승인 기준

### 빠르게 승인 가능한 경우
아래 조건을 모두 만족하면 빠르게 승인 가능하다.

- Level 1 또는 Level 2
- final-report.md가 명확하다
- 고위험 영역 변경이 없다
- 테스트 결과가 기록되어 있다

### 상세 검토가 필요한 경우
아래 중 하나라도 해당하면 상세 검토한다.

- Config 변경
- Security/Auth 변경
- Cache/Redis 변경
- DB 변경
- OpenAPI 변경
- Dependency 추가 또는 업그레이드

### 반려 가능한 경우
아래 중 하나라도 해당하면 반려할 수 있다.

- agent-log 누락
- 필수 파일 누락
- final-report.md 부실
- Self-Check 누락
- Config/Library 변경인데 영향 분석 없음
- API 변경인데 OpenAPI 없음
- 고위험 변경인데 롤백 계획 없음

---

## 롤백 원칙

- 모든 작업은 Git 기준으로 되돌릴 수 있어야 한다.
- 위험한 변경은 작은 단위 커밋으로 나누는 것을 권장한다.
- 승인 전 작업은 main에 병합하지 않는다.
- 마음에 들지 않거나 기준 미달이면 브랜치 폐기 또는 revert/reset으로 롤백한다.

예시:
```bash
git switch main
git branch -D agent/backend-user-cache-refactor
```

또는:
```bash
git revert <commit>
```

---

## 코드 주석 원칙

설정, 보안, 캐시, 공통 로직, 장애 대응 코드에는 변경 이력 주석을 남기는 것을 권장한다.

예시:
```java
/**
 * CacheConfiguration
 * ------------------------------------------------------------------
 * Redis/Redisson 기반 JCache 설정
 *
 * 변경 이력:
 *  - 2026-03-20: C-1 리팩토링
 *    → 인증 캐시 제거 및 TTL 재설계
 * ------------------------------------------------------------------
 */
```

원칙:
- 최신 변경을 위에 둔다.
- 날짜 + 이슈 키 + 변경 요약 형태로 쓴다.
- 단순 코드 설명이 아니라 변경 이유와 맥락이 드러나게 한다.

---

## API 문서 원칙

- API 계약 변경 시 OpenAPI를 반드시 갱신한다.
- Swagger 등 도구에서 바로 읽을 수 있는 형식을 유지한다.
- agent-log에는 OpenAPI 전문을 복사하지 않고, 변경 배경과 영향만 한국어로 요약한다.

---

## 운영 원칙

이 워크플로우의 목적은 리뷰어가 모든 결과를 하나하나 직접 판단하는 구조를 줄이고, 규칙과 문서를 통해 검토 범위를 축소하는 데 있다.

핵심 원칙:
- 코드를 먼저 보지 않는다.
- 요약과 영향 범위를 먼저 본다.
- 고위험 변경만 깊게 본다.
- 나머지는 규칙과 문서로 통제한다.

---

## 한 줄 원칙

> 롤백은 안전장치이고, 피로를 줄이는 것은 표준화된 작업 흐름과 요약 문서다.
