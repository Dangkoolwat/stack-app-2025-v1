# PR Review Checklist

## 목적
이 문서는 리뷰어가 모든 변경을 세부적으로 보지 않아도 되도록, 최소한의 핵심 기준으로 PR을 검토하기 위한 체크리스트를 정의한다.

---

## 리뷰 순서

1. final-report.md 확인
2. 변경 파일 목록 확인
3. 고위험 변경 여부 확인
4. 필요한 경우에만 상세 코드 확인

---

## Reviewer Quick Check

아래 3가지를 가장 먼저 본다.

- [ ] 위험한 변경인가? (Config / Security / Cache / DB / Dependency / OpenAPI)
- [ ] 아키텍처를 깨는가?
- [ ] 롤백 가능한가?

---

## 필수 문서 확인

- [ ] agent-log 존재
- [ ] 필수 파일 6개 존재
- [ ] final-report.md 내용이 명확함
- [ ] self-check.md 존재
- [ ] 고위험 변경 시 영향 분석 포함

---

## 구현 품질 확인

- [ ] 문제 정의가 명확함
- [ ] 해결 방식이 과하지 않음
- [ ] 기존 패턴을 우선 따름
- [ ] 불필요한 복잡성 없음
- [ ] 변경 범위가 지나치게 크지 않음

---

## 유지보수성 확인

- [ ] 코드 책임이 명확함
- [ ] 변경 이유가 문서 또는 코드 주석에 남아 있음
- [ ] 추후 수정자가 이해 가능함
- [ ] 큰 리팩터링이 필요한 이유가 설명됨

---

## 보안 / 설정 / 인프라 확인

- [ ] 민감 정보 로그 없음
- [ ] 인증/인가 처리에 이상 없음
- [ ] 캐시 정책 검토 완료
- [ ] Config 변경 시 영향 분석 완료
- [ ] 라이브러리 변경 시 호환성 검토 완료

---

## API / 계약 확인

- [ ] API 변경 없음 또는 OpenAPI 업데이트 완료
- [ ] 기존 계약을 깨는 경우 명시됨
- [ ] 프론트/백엔드 영향 범위가 기록됨

---

## 테스트 확인

- [ ] 테스트 결과가 기록됨
- [ ] 회귀 위험이 있는 부분이 검토됨
- [ ] 수동 테스트가 필요한 경우 이유가 적혀 있음

---

## 반려 기준

아래 중 하나라도 해당하면 반려 가능하다.

- [ ] agent-log 없음
- [ ] final-report.md 부실
- [ ] 고위험 변경인데 영향 분석 없음
- [ ] OpenAPI 변경 누락
- [ ] 롤백 계획 없음
- [ ] 아키텍처 위반이 명확함

---

## 리뷰 원칙

- 모든 변경을 깊게 보지 않는다.
- 고위험 변경만 깊게 본다.
- 문서와 체크리스트로 대부분을 걸러낸다.
- 기준을 만족하지 않으면 판단보다 반려를 우선한다.
