# 제안 방안

## 방안 1

Redis 캐시를 DTO/read-model 전용으로 재정의하고 Hibernate L2 Redis 사용을 중단한다.

장점
- Jackson 3, Hibernate proxy, LazyLoading 결합 리스크를 크게 줄일 수 있음
- 캐시 fallback/무효화 설계를 서비스 단위로 명확히 둘 수 있음

단점
- 일부 서비스/컨트롤러 반환 경계와 테스트를 함께 손봐야 함

## 방안 2

Hibernate L2 Redis 를 유지하되 캐시 직렬화 설정만 보강한다.

장점
- 변경 범위가 상대적으로 작음

단점
- 근본 원인인 엔티티/프록시 직렬화 의존이 남음
- 이후 프레임워크 업그레이드 때 같은 문제가 반복될 가능성이 큼

# 선택

방안 1을 채택했다.

# 선택 이유

- 이미 인증 캐시가 DTO 패턴으로 안정화된 선례가 있음
- 공통코드/업로드 조회도 DTO 응답으로 바꾸는 편이 장기적으로 안전함
- 전역 Jackson 우회 설정을 제거하고 API 직렬화 규칙을 정상화할 수 있음
